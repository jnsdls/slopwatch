# Shipping and updating a Rust/GPUI macOS app

Research for [#32](https://github.com/jnsdls/slopwatch/issues/32). Sources read on 2026-10-02. Zed links are pinned to [`c83abe7`](https://github.com/zed-industries/zed/tree/c83abe7d0e060de08db386fbf86f7e95bfe6cb09) and Sparkle links to [`fd34238`](https://github.com/sparkle-project/Sparkle/tree/fd34238cbbc5db4a6e8343c62ae4dea939b06ea4). "SMAppService.h" means the header in the macOS 26.2 SDK that ships with Xcode, at `ServiceManagement.framework/Headers/SMAppService.h`. Nothing here was tested on a machine. Forum quotes came through page fetches, so check the wording before quoting them elsewhere.

## Short answer

- Signing and notarizing a Rust `.app` is a shell script, not a tool. Zed uses its cargo-bundle fork only to lay out the bundle, copies extra binaries into `Contents/MacOS` by hand, signs each one inside-out with `--timestamp --options runtime`, signs the app, builds a DMG, and notarizes and staples only the DMG. We can copy that shape with the daemon in place of Zed's `cli`.
- SMAppService needs macOS 13, a signed app, the agent plist in `Contents/Library/LaunchAgents`, and `BundleProgram` pointing at the daemon by a bundle-relative path. Agents don't need notarization to register. Only daemons do.
- An unsigned build should fail `register()` with `kSMErrorInvalidSignature`. For ad-hoc builds, no Apple source says yes or no. DTS tells people to sign with an Apple-issued identity and says ad-hoc signing causes lost approvals. Dev builds should sign with a free Apple Development identity.
- Updaters: Zed's updater is GPL, `publish = false` and tied to Zed's backend, so we can copy its pattern but not use it. Sparkle 2 works with GPUI because GPUI runs a real `NSApplication`, and two young Rust wrappers exist. A hand-rolled check against GitHub Releases needs a manifest, a Team ID signature check and a whole-bundle swap.
- The handoff in ADR 0009 has a gap. SMAppService.h says that after the agent executable changes, the app "must" re-register the service "or it may not launch", and recommends `unregister` before `register`. A plain `restart` that leaves the respawn to launchd may not start the new binary. This holds for every updater, because Sparkle's maintainer says agent updates are the app's job.

## Signing and notarization

### What Apple requires

- Notarization rejects anything where an executable lacks Developer ID signing, hardened runtime or a secure timestamp, or carries `get-task-allow`. Ad-hoc and Apple Development signatures are rejected. [Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple: Resolving common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues).
- Sign inside-out, one item at a time, and don't use `--deep` to sign. `--deep` applies one set of entitlements to everything. `man codesign` marks it deprecated for signing as of macOS 13. Apple's example signs a nested daemon with `-o runtime -i <identifier>`. [Apple: Creating distribution-signed code](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac), [Quinn: --deep considered harmful](https://developer.apple.com/forums/thread/129980).
- Helper executables go in `Contents/MacOS` or `Contents/Helpers`. [Apple: Placing content in a bundle](https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle).
- `xcrun notarytool submit <file> --wait` takes either a keychain profile or an App Store Connect API key (`--key`, `--key-id`, `--issuer`). CI wants the API key. It accepts zip, DMG and pkg. `stapler` can staple an app, DMG or pkg but not a zip. [Apple: Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
- A DMG can carry a signature and a zip can't. Apple's order is sign the app, build the DMG, sign the DMG, notarize, staple. [Apple: Packaging Mac software](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

### What Zed does

All from [`script/bundle-mac`](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac).

- It installs Zed's own cargo-bundle fork, `zed-industries/cargo-bundle` on branch `zed-deploy` ([L61-L66](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L61-L66)), and runs it with `CARGO_BUNDLE_SKIP_BUILD` after a `sed` swaps in the release channel's metadata ([L102-L107](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L102-L107)). Each channel has its own bundle ID, with `dev.zed.Zed-Dev` for dev builds ([crates/zed/Cargo.toml L281-L311](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/zed/Cargo.toml#L281-L311)).
- It builds `zed` and `cli` with plain cargo, strips them, and copies both into `Contents/MacOS` ([L350-L356](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L350-L356)).
- In CI it imports a base64 `.p12` into a temporary keychain ([L124-L145](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L124-L145)). The secrets are `MACOS_CERTIFICATE` and the three `APPLE_NOTARIZATION_*` API key values ([release.yml L547-L551](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/.github/workflows/release.yml#L547-L551)).
- It signs `cli` and a bundled `git` with `--timestamp --options runtime` and no entitlements, then `Contents/MacOS/zed` with entitlements, then the app ([L208-L211](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L208-L211)). It passes `--deep` on single Mach-O files, where it does nothing. I wouldn't copy that.
- Without a certificate it falls back to `codesign --force --deep --sign -`, an ad-hoc signature ([L224-L226](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L224-L226)). Zed has no login item, so ad hoc costs it nothing. It would cost us.
- It builds a UDZO DMG with an `/Applications` symlink ([L250-L273](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L250-L273)), signs it, runs `notarytool submit --wait` with the API key, and staples the DMG ([L277-L281](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/script/bundle-mac#L277-L281)). The app inside is never stapled on its own.

### cargo-bundle upstream

Upstream cargo-bundle now signs in-process through `apple-codesign` and can sign the app and DMG, but it doesn't notarize. It has one entitlements setting for the whole bundle, and no setting that puts a second binary in `Contents/MacOS` or a plist in `Contents/Library/LaunchAgents` ([Readme L102, L263-L287](https://github.com/burtonageo/cargo-bundle/blob/787d710686480cea32960bcd4d9f762c2f9bbd53/Readme.md#L263-L287)). So we need the post-bundle copy and re-sign step either way, as Zed has.

### Entitlements

Hardened runtime blocks JIT and unsigned executable memory unless an entitlement allows it. Entitlements go on executables only ([Apple: Hardened runtime](https://developer.apple.com/documentation/security/hardened-runtime)). Zed's [`zed.entitlements`](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/zed/resources/zed.entitlements) has `cs.allow-jit` and `cs.allow-unsigned-executable-memory`. The second came back in a commit titled "Re-enable language plugin functionality", which points at the Wasm extension runtime rather than GPUI. GPUI compiles its Metal shaders at build time unless the `runtime_shaders` feature is on ([gpui_apple/build.rs L20-L22](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/gpui_apple/build.rs#L20-L22)). My read is that slopwatch needs no `cs.*` exceptions, but I found no Apple statement that settles it. The daemon needs hardened runtime and a timestamp like every other executable in the bundle.

## SMAppService

- Available from macOS 13. "Apps that use SMAppService APIs must be code signed." `register()` returns `kSMErrorInvalidSignature` for a bundle that isn't. SMAppService.h L49, L65, L168.
- The agent plist lives in `Contents/Library/LaunchAgents`. It uses `BundleProgram` with a path relative to the bundle, so the app can move. [Apple: agent(plistName:)](https://developer.apple.com/documentation/servicemanagement/smappservice/agent(plistname:)), SMAppService.h L103-L107. `man launchd.plist` says `BundleProgram` works only for plists installed through SMAppService.
- `AssociatedBundleIdentifiers` is for legacy plists outside the bundle. An agent inside the bundle belongs to the app automatically. [Apple: Updating helper executables from earlier versions of macOS](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos).
- Notarization is required only for apps that contain LaunchDaemons. SMAppService.h L55.
- DTS says to sign the helper and the app with the same Apple-issued identity, and to check both with `codesign -d -vvv` so Background Task Management can tie the agent to the app. [Thread 799910](https://developer.apple.com/forums/thread/799910), [thread 757463](https://developer.apple.com/forums/thread/757463).
- `status` is `notRegistered`, `enabled`, `requiresApproval` or `notFound`. `requiresApproval` also comes back when the user turns the item off later in System Settings. Quinn's test reads `notFound` before the first registration, so treat it as "never registered". SMAppService.h L30-L34, [thread 721737](https://developer.apple.com/forums/thread/721737).
- `register()` starts an agent right away and at every later login. It runs once per user, from a user context. SMAppService.h L152-L166. launchd still launches on demand, so the plist needs `RunAtLoad` or `KeepAlive` for a daemon that should always run ([thread 750528](https://developer.apple.com/forums/thread/750528)).
- The first registration posts a "Background Items Added" notification that apps can't suppress ([thread 725982](https://developer.apple.com/forums/thread/725982)). `openSystemSettingsLoginItems()` sends the user to the toggle when status is `requiresApproval`.
- Rust bindings exist. `objc2-service-management` 0.3.2 exposes `agentServiceWithPlistName`, `registerAndReturnError`, `unregisterWithCompletionHandler`, `status` and `openSystemSettingsLoginItems` ([docs.rs](https://docs.rs/objc2-service-management/latest/objc2_service_management/struct.SMAppService.html)).
- launchd refuses to run a quarantined helper when the app belongs to another user, the Homebrew cask case ([thread 723134](https://developer.apple.com/forums/thread/723134)).

### Ad-hoc and dev builds

- Unsigned: per the header, `register()` fails. Inferred from SMAppService.h L49 and L168, not tested.
- Ad hoc: no first-party yes or no. DTS says ad-hoc signing leads to "problems like this", meaning the user loses the background permission after restarts ([thread 799910](https://developer.apple.com/forums/thread/799910)). An ad-hoc signature has no Team ID and no stable designated requirement, so every rebuild looks like a new program ([thread 782645](https://developer.apple.com/forums/thread/782645), [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)).
- Apple's suggested dev identity is Apple Development, which a free Personal Team provides ([thread 782645](https://developer.apple.com/forums/thread/782645)).
- Background Task Management matches items by bundle ID, Team ID and launchd label. `sfltool dumpbtm` shows what it recorded ([Apple: Managed login items](https://support.apple.com/guide/deployment/depdca572563/web)). The separate dev label from ADR 0009 should come with a separate bundle ID, as Zed does with `dev.zed.Zed-Dev`. No Apple doc covers this case directly.

## Updaters

### Zed's updater

- It polls every hour, every 15 minutes on nightly ([auto_update.rs L47-L48](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/src/auto_update.rs#L47-L48)). It calls `GET /releases/{channel}/{version|latest}/asset` on Zed's cloud and gets back `{version, url}` ([L677-L738](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/src/auto_update.rs#L677-L738)). Stable compares semver, nightly compares commit SHAs ([L868-L902](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/src/auto_update.rs#L868-L902), [L960-L968](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/src/auto_update.rs#L960-L968)).
- It downloads `Zed.dmg`, mounts it with `hdiutil attach -nobrowse`, and runs `rsync -av --delete` from the mounted app into the running app ([L1197-L1251](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/src/auto_update.rs#L1197-L1251)). That rewrites the live bundle file by file. It does no checksum or signature check of its own.
- The "Restart to update" button calls `cx.restart()`. On macOS GPUI spawns `bash -c 'while kill -0 $pid; do sleep 0.1; done; open "$app_path"'` and quits ([gpui_macos/src/platform.rs L614-L656](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/gpui_macos/src/platform.rs#L614-L656)). We get that relaunch for free from GPUI whichever updater we pick.
- We can't depend on it. The workspace sets `publish = false`, the crate pulls in `client`, `db`, `settings` and `workspace`, and it is GPL-3.0-or-later ([Cargo.toml](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/auto_update/Cargo.toml)).
- Apple says not to do what it does. "Do not modify an app's bundle after it's been launched" ([Quinn, thread 761436](https://developer.apple.com/forums/thread/761436)). In-place writes to signed files can crash with "Code Signature Invalid", because the kernel caches signature data per file ([Apple: Updating Mac software](https://developer.apple.com/documentation/security/updating-mac-software)).

### Sparkle 2

- GPUI subclasses `NSApplication`, sets a delegate and runs the normal AppKit loop ([platform.rs L80-L87, L552-L591](https://github.com/zed-industries/zed/blob/c83abe7d0e060de08db386fbf86f7e95bfe6cb09/crates/gpui_macos/src/platform.rs#L552-L591)). Sparkle's standard UI has what it needs.
- Setup is an embedded, signed `Sparkle.framework` in `Contents/Frameworks`, an rpath of `@loader_path/../Frameworks`, and `SUFeedURL` and `SUPublicEDKey` in Info.plist. `generate_keys` keeps the EdDSA private key in the login keychain, and `generate_appcast` signs archives and writes the feed. [Sparkle: Documentation](https://sparkle-project.org/documentation/), [Sparkle: Publishing](https://sparkle-project.org/documentation/publishing/).
- A non-sandboxed app skips the XPC services ([Sparkle: Sandboxing](https://sparkle-project.org/documentation/sandboxing/)).
- On install, Sparkle waits for the app to quit ([AppInstaller.m L394-L416](https://github.com/sparkle-project/Sparkle/blob/fd34238cbbc5db4a6e8343c62ae4dea939b06ea4/Autoupdate/AppInstaller.m#L394-L416)), checks the EdDSA signature or code-signing identity ([SUUpdateValidator.m L295-L302](https://github.com/sparkle-project/Sparkle/blob/fd34238cbbc5db4a6e8343c62ae4dea939b06ea4/Sparkle/SUUpdateValidator.m#L295-L302)), swaps the whole bundle with `renamex_np(RENAME_SWAP)` ([SUPlainInstaller.m L235-L244](https://github.com/sparkle-project/Sparkle/blob/fd34238cbbc5db4a6e8343c62ae4dea939b06ea4/Autoupdate/SUPlainInstaller.m#L235-L244)), and relaunches through `NSWorkspace`. The running daemon keeps its old vnode through the swap. Sparkle doesn't document that, I read it from the code.
- Sparkle waits only on the app, not on other processes in the bundle. Its maintainer says "Updating a bundle while it's already in use is not something Sparkle tries to support" and that launch agents are updated "by the app through other means" ([discussion 2423](https://github.com/sparkle-project/Sparkle/discussions/2423)). In [discussion 2572](https://github.com/sparkle-project/Sparkle/discussions/2572) he advises against hanging agent reloads on Sparkle's delegate hooks, because they don't fire on every path. The app should notice the version change itself. Our `hello` build-id check already does that.
- Rust wrappers are young. [`sparklers`](https://github.com/slint-ui/sparklers) 0.1.1 from slint-ui wraps `SPUStandardUpdaterController` with objc2. [`sparkle-updater`](https://github.com/ahonn/tauri-plugin-sparkle-updater) 0.1.0 lives inside a Tauri plugin. A small objc2 binding of our own would be about as much code.

### Hand-rolled

- Host releases on GitHub. `/releases/latest/download/<asset>` is a static URL with no API rate limit, so publish a small JSON manifest as an asset next to the DMG or zip ([GitHub: Linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)). The REST API allows 60 unauthenticated requests per hour ([GitHub: Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)).
- Verify the download with `SecStaticCodeCheckValidity` against `anchor apple generic and certificate leaf[subject.OU] = "<TEAMID>"` ([Apple: SecStaticCodeCheckValidity](https://developer.apple.com/documentation/security/secstaticcodecheckvalidity(_:_:_:))). That replaces Sparkle's EdDSA check with our Team ID.
- Replace the whole bundle, never files inside it. Quinn's recipe is a small helper with no dependency on the bundle that swaps it after the app quits and relaunches it ([thread 758329](https://developer.apple.com/forums/thread/758329)). Files our own HTTP client downloads carry no quarantine flag ([thread 730314](https://developer.apple.com/forums/thread/730314)).
- Our app may write its own bundle because the Team IDs match. `NSUpdateSecurityPolicy` changes that rule ([Apple: NSUpdateSecurityPolicy](https://developer.apple.com/documentation/bundleresources/information-property-list/nsupdatesecuritypolicy)).

## Handoff to the daemon

The flow in ADR 0009 is the same for all three updaters. The bundle gets replaced, the GUI relaunches, sees a new build id in `hello`, sends `restart`, and the daemon exits. What happens next is the open question.

- SMAppService.h L59-L62: "If an app updates either the plist or the executable for a LaunchAgent or LaunchDaemon, the SMAppService must be re-registered or it may not launch. It is recommended to also call unregister before re-registering if the executable has been changed."
- [Thread 758329](https://developer.apple.com/forums/thread/758329): after a self-update replaced the bundle, a `BundleProgram` daemon "never actually launches". DTS says the system weighs running from the bundle against "making sure it can't be tricked into running the wrong daemon". Unresolved.
- [Thread 804561](https://developer.apple.com/forums/thread/804561): DTS says that with `BundleProgram` there is only one copy of the binary, so killing the old process after an update should load the new one. That supports ADR 0009 as written, and it conflicts with the header.
- [Thread 768592](https://developer.apple.com/forums/thread/768592): `register()` alone left the old binary running, and `unregister` followed at once by `register` failed with "Operation not permitted" until the poster added a delay of about 500 ms. The async `unregister` completion handler is the documented point to register again (SMAppService.h L214-L218).
- [Thread 745412](https://developer.apple.com/forums/thread/745412): re-registering kept the path of the first registered bundle. Quinn asked for a bug report, FB13570494.

What this means for the design: on a build-id mismatch the GUI should send `restart`, then call `unregister`, wait for its completion handler, and call `register`. The daemon's crash-only startup doesn't change. Only the GUI's half of the handoff grows. A cheaper variant tries `restart` alone and falls back to re-registering if no `hello` with the new build id arrives in a few seconds. I'd take the first one, because the header says "must".

## Open points

- Whether an ad-hoc-signed app can `register()` an agent at all, and whether its approval survives a rebuild. A test with two ad-hoc builds and `sfltool dumpbtm` would settle it. Either way, Apple Development signing for dev builds avoids the question.
- Whether `unregister` then `register` on every update shows the "Background Items Added" notification again or asks for approval again. Quinn says the user's decision is remembered ([thread 802443](https://developer.apple.com/forums/thread/802443)), but nobody tested it across a changed binary.
- Whether a plain `restart` after a notarized, same-team bundle swap starts the new daemon. The header and DTS disagree. An N to N+1 update test on a clean VM, as DTS suggests in thread 758329, answers it.
- Whether the daemon needs its own `-i <identifier>` when signed. Apple's example passes one for a nested daemon. Zed's `cli` gets none.
- Whether GPUI needs `cs.allow-jit` for anything. Build-time shaders suggest not. Confirm by running a notarized build with no entitlements.
