# The daemon is a separate, crash-only process

Amended by ADR 0013: the daemon doesn't post notifications. The GUI does, and the daemon launches it in the background when no GUI is connected. Amended by [#56](https://github.com/jnsdls/slopwatch/issues/56): on an ad-hoc build the handoff registers a second time when the first register brings up nothing (see "What the first build showed").

The daemon always runs as the launchd login agent registered from the `.app` (`SMAppService.agent`), and the GUI is only ever a client of it. It has no graceful shutdown path. Whether it crashed, the Mac rebooted or an update replaced the binary, it comes back the same way. It does one poll first. If a Run's head moved while it was down, that Run ends (pushed if the new SHA is in the push journal, superseded otherwise). Otherwise it keeps the settled Outcomes and respawns the interrupted Steps from scratch in the same Run. An update is just a restart. When the GUI sees a different build id in `hello`, it sends `restart`, and the daemon kills its Step process groups and exits. The GUI then calls `unregister` on the agent, waits for the completion handler, and calls `register`, so launchd starts the new binary. One recovery path that runs on every update stays tested. A second path that only runs after a crash would rot.

## Considered options

- Run the engine inside the GUI when no agent is running, as zeron's headed mode does. Two engines could then race over one state store, and Runs stop when the GUI quits.
- Drain before exiting: start no new Steps and wait for running ones to settle. Agent Steps can run for 20 minutes or more, so updates would lag, and the drain code would be one more path to keep correct.
- End an interrupted Run as cancelled and start a new Run on the same SHA. It does the same work, but every reboot leaves a cancelled Run in Run history, and cancelled means the developer cancelled it.

## Consequences

- Respawning an interrupted Step isn't an auto-retry, because the Step never reported. A Step interrupted by two restarts in a row gets `error(daemon_restart)` and an Escalation, so a Step that crashes the daemon can't loop it.
- Every Effect gets an intent row (Effect, expected head OID, and the intended tree for a commit) before the daemon calls GitHub, and is marked done after. On restart the daemon reconciles open intents against GitHub. A commit whose parent is the expected OID and whose tree matches goes into the push journal. Otherwise a lost SHA would read as an outside push, reset the Fix round count and give the Run the wrong end reason. Comments carry a hidden `<!-- slopwatch:effect=<id> -->` marker so the daemon can find them before reposting. Merge reads PR state, label and rerun are redone, and rebase puts the PR back in its rebasing state.
- Each Step runs in its own process group, and the daemon records the pgid and process start time. On restart it kills leftover groups (the start time guards against PID reuse) and deletes the interrupted Steps' worktrees.
- An update throws away the work of any Step in flight. Updates are rare, so that costs little.
- The daemon holds an exclusive `flock` on its data dir. Dev builds use their own data dir, socket, launchd label and bundle ID (`com.jnsdls.slopwatch.dev`), because Background Task Management keys its records on bundle ID, Team ID and label.
- Re-registering on every update follows `SMAppService.h`, which says an app "must" re-register an agent after its executable changes "or it may not launch", and recommends `unregister` first. Apple DTS has said in one forum thread that killing the old process is enough. The N to N+1 test in "What the first build showed" bore the header out. Retrying only when no new `hello` arrives would be a second path that rarely runs, and that is what this ADR avoids. On an ad-hoc build the retry runs on every update, so it stays until builds carry a Team ID.

## What the first build showed

[#56](https://github.com/jnsdls/slopwatch/issues/56) ran the install script on macOS 15.7 with ad-hoc signatures (`codesign -s -`), first for a dev build and then for a release build next to it.

- `SMAppService.register()` accepts an ad-hoc build. Neither executable has entitlements, both carry the hardened runtime flag, and both run.
- A plain kill isn't enough, so the header was right. After a rebuild, launchd's KeepAlive relaunch of the new `slopwatchd` dies with "Launch Constraint Violation". Background Task Management pinned the agent's launch constraint to the old build's code identity, and an ad-hoc identity is its cdhash.
- One `unregister` and `register` isn't enough either. `register` reuses the old Background Task Management record, launch constraint included, so the new daemon still can't start. About 10 s later, after launchd's next failed launch, macOS creates a new record for the new code, and a second `register` starts the new daemon. The GUI therefore registers again if no `hello` from its own build arrives within 20 s, at most twice per launch. On an ad-hoc build this runs on every update, so it isn't the rarely run path the consequence above warns about. A handoff takes 20 to 25 s.
- "Background Items Added" came back. Each rebuild creates a new record, and macOS posted the notification for the first install and the next two updates. It posted none for the four updates after that in the same session, so it looks rate-limited rather than gone.
- Login Items approval holds across rebuilds. System Settings lists one `slopwatch-dev` entry, still on, instead of one per build. macOS ignores `AssociatedBundleIdentifiers` for an executable with no Team ID and says so in the log, so the entry carries the bundle's name and a generic icon.
- Keychain access does not hold. A test binary that reads back an item an earlier ad-hoc build stored blocks on a Keychain prompt, even when it asks for no UI. The same test signed with a self-signed certificate prompts too, because without a Team ID the item's access list names the writer's cdhash. The daemon would hit that prompt after every rebuild, so ADR 0014 has it keep Secrets through `/usr/bin/security` instead.
- `SMAppService` status can't tell whether the daemon runs. After `launchctl bootout`, or after deleting and reinstalling the app, it still says enabled while launchd has no job. So the GUI doesn't trust the status: when nothing answers at launch it runs the same unregister and register steps, unless the status says the developer turned the agent off in Login Items.
- The daemon doesn't need its own `codesign -i` to register. Without one, its identifier is the linker's `slopwatchd-<hash>`, which changes every build, so the script signs it as `<bundle id>.daemon` to keep logs and prompts readable.
- A self-signed certificate fixes none of this. codesign accepts an untrusted self-signed identity, and the designated requirement becomes the certificate instead of the cdhash. The launch constraint, the second `register` and the Keychain prompt all behaved the same, because what macOS keys on is the Team ID and a self-signed certificate has none. v1 stays ad-hoc. A free Apple Development identity has a Team ID, so it is the change that should retire the second `register` and the Keychain prompt. Once builds carry one, the 20 s retry becomes the rarely run path this ADR rules out and should go. Creating the identity takes the developer's Apple account in Xcode.
- The dev build installs to `~/Applications/slopwatch-dev.app`, not `target/dev/` as [macOS distribution and updates](https://github.com/jnsdls/slopwatch/issues/33) planned. Background Task Management remembers the path it first registered, and a path inside one worktree's `target/` would move as worktrees come and go.
- Notification permission across rebuilds is still untested, because the GUI doesn't ask for it yet. It belongs to the notifications ticket.
